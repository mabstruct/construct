<scope_decision>
**Q1 resolution — recorded so it is a decision, not a drift.**

D-10 requires the sidebar display be "computed by calling into `llm/config.py`'s resolution order". But
`llm/config.py` exposes **no public path resolver**: `load_llm_config()` returns a parsed `LlmConfig`
with no path attribute, the resolution order is inlined at lines 70-76, and the env-var name lives in a
private `_ENV_CONFIG_OVERRIDE`. There is no function the UI can call.

**Decision: extract `resolve_llm_config_path()` (14-RESEARCH.md Q1 Option A).** This is a **pure
extraction of existing logic** — no behavior change, no signature change, no new capability. It exposes
a value the module already computes. It is authorized because:
- It is the only option that delivers D-10's stated goal. Replicating the order in the UI (Option B)
  recreates the exact drift D-10 exists to close and duplicates a private constant. Hardcoding the
  default (Option C) ignores `CONSTRUCT_LLM_CONFIG`, which criterion 3 names explicitly.
- It is same-tier: `llm/config.py` is already the LLM-config authority. It is **not** in the drift set
  named by 14-CONTEXT.md `<specifics>` (`schemas/`, `storage/`, `services/`).
- `14-VALIDATION.md` Wave 0 already names `resolve_llm_config_path()` as a required deliverable, so the
  extraction is pre-recorded in a committed phase artifact.

**Expected test count after this plan: 443** (439 baseline + 4). ROADMAP criterion 5 is a floor
("≥439"), so the delta is intentional. Research assumption A2 is discharged by stating it here.

**Deliberately NOT extended:** `install_root` (`streamlit_app.py:23`) has the identical dead-write
defect — `st.session_state["install_root"]` is read nowhere — but D-11 extended scope to
`provider_override` explicitly and stopped there. Record `install_root` as a deferred observation in the
SUMMARY; do not fix it. `st.session_state["workspace_path"]` IS read (`dashboard.py:86`,
`gate_review.py:71`) and must not be touched.
</scope_decision>
