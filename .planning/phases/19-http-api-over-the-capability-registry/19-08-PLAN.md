<objective>
Make runs enumerable, so no run becomes unreachable after its id is lost — and make CLI, MCP and
HTTP gain that at the same moment.

RESEARCH established two things that shape this. First, the enumeration primitive: the checkpoint
library's own listing call accepts a null config and does enumerate across threads, but it yields
one tuple *per checkpoint*, deserializing every state blob and every pending write, ordered
globally with no grouping — so a workspace with a few long runs makes the endpoint visibly slow
and the ordering is not what a run list wants. A distinct-thread-id query against the schema the
checkpointer itself creates is the cheap primitive. Second, and more important: enumeration spans
**three** stores, not two. A daily run persists a JSON receipt and never pauses, so a listing built
only on checkpoint databases reports zero daily runs while the daily inspect capability happily
answers for them — HTTP-07's own stated failure mode reproduced inside its own fix.

Purpose: the alternative shapes were a browser-only checkpoint reader (the fork this phase's goal
sentence forbids) and widening the existing status capability (which conflates two questions and
changes an output shape callers already depend on). A new capability is what makes the third-peer
principle actually pay off.
Output: `workflow.list`, spanning three stores, reachable from every surface.
</objective>

## Named decisions recorded by this plan

- **D-13 — run enumeration is a new registry capability, `workflow.list`, with both a CLI name and
  an MCP tool name.** HTTP picks it up free through the envelope, and CLI and MCP gain run listing
  at the same moment, which is the third-peer principle paying off rather than HTTP getting a
  private feature. Widening the existing status capability was rejected because it conflates two
  questions and changes an output shape callers already read; a browser-side checkpoint reader was
  rejected because it is a browser-only feature over durable state the CLI cannot see. —
  *Reversibility: costly* — a registered capability's id and output shape become a consumed
  contract on three surfaces at once.
- **D-25 — the listing is O(runs), and that is stated rather than discovered.** Per-run status
  comes from the existing inspect primitives, each of which deserializes one checkpoint, so a
  workspace with many runs costs one deserialization per run. That is acceptable for a local
  proof of concept and is recorded in the module docstring so it is a known property rather than a
  surprise.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller-supplied workspace id -> checkpoint database paths | The listing opens database files under a workspace derived from caller input |
| durable run state -> listing body | Run ids, statuses and checkpoint handles are rendered back to an untrusted caller |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-19-03 | Tampering / Info disclosure | workspace resolution for the listing | high | mitigate | The capability is workspace-scoped and classified in the field map, so it inherits the seam's shape-then-allowlist gates unchanged; no new path handling is introduced |
| T-19-05 | Information disclosure | listing body contents | medium | mitigate | Entries carry run ids, workflow names, statuses and checkpoint handles — never database paths or receipt file paths; the parity leak assertion covers the rendered body |
| T-19-23 | Repudiation | a store silently unread | high | mitigate | The fixture creates one run of each of the three workflow types and the test asserts three distinct workflow values, so a checkpoint-only implementation fails rather than reporting zero daily runs |
| T-19-24 | Denial of service | listing cost on a workspace with many runs | low | accept | One checkpoint deserialization per run (D-25), acceptable for a local single-user proof of concept and stated in the module docstring rather than discovered |
</threat_model>
