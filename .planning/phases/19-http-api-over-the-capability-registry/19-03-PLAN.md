<objective>
Build the shared result and error boundary that HTTP-04 turns into a cross-surface contract, and
close the leaks that would make criterion 3 fail on a request that succeeded.

RESEARCH measured 43 handlers that stringify a bound exception; 14 of them demonstrably leak an
absolute path (`str(OSError)` embeds the full path), and every one of them reaches a serialized
body. Separately, two pipelines write `str(root.resolve())` into a result's `data` on the
**success** path, where no exception-boundary sanitizer will ever see it.

Purpose: criterion 3 says "no raw exception text or filesystem paths in the body" across three
surfaces. That has to hold mechanically, and it has to hold for a 200 as well as a 422. Landing
the boundary before the adapter exists means the HTTP route never has a stringifying arm to
inherit — and it closes the MCP surface's last unguarded one as a side effect.
Output: `capabilities/results.py`, MCP routed through it, the two success-path leaks fixed, and a
shrink-only baseline that stops the remaining sites from regrowing.
</objective>

## Named decisions recorded by this plan

- **D-16 — the leak is closed on three separate tracks, not folded into one task.** (a) A shared
  sanitizing boundary, which fixes every `services/knowledge.py` and `services/validation.py`
  message and the MCP catch-all in one change. (b) A shrink-only baseline over the remaining
  source sites, so they cannot regrow — the `UNRESOLVED_DIRECT_CALLERS` shape Phase 18 D-23 already
  established in this repo. (c) The **success-path** data leaks, tracked separately and fixed
  here, because an exception-boundary sanitizer structurally cannot see them and folding them into
  a sanitizer task is how they get quietly missed. — *Reversibility: reversible.*
- **D-19 — a capability emits the workspace *name*, and a local caller appends the absolute path.**
  This is the convention `cli.py` already states for reason strings ("this is the *local* caller,
  so it appends the path itself"), extended to result `data`. The name is also exactly the
  workspace id HTTP-03 addresses by, so the emitted value gains meaning rather than losing it.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| capability result -> serialized body | Everything crossing here is read by an agent or a browser; it is the last place a path or a raw exception can be stopped |
| exception object -> reason string | The exception's own text is attacker-influenced (it can embed submitted values) and environment-revealing (it embeds paths) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-19-05 | Information disclosure | success-path result `data` | medium | mitigate | `graph.status` and `bridge.detect` emit the workspace name, not a resolved absolute path; asserted against a successful body, not only an error body |
| T-19-06 | Information disclosure | MCP catch-all and every serialized message | medium | mitigate | `sanitize_exception` at the shared boundary; the serializer keeps no stringifying fallback, so an unprojectable value is a bug to fix rather than a path to coerce |
| T-19-15 | Repudiation | leak sites regrowing after the fix | medium | mitigate | Shrink-only baseline keyed per function, failing on both a new offender and a stale entry, with a non-vacuity assertion so it cannot pass by scanning nothing |
| T-19-16 | Information disclosure | caller payload echoed back in a validation reason | high | mitigate | Reason strings are built only through `from_validation_error`, which already sets `include_input=False` and `include_context=False`; plan 19-07 extends this rule to the HTTP validation handler, whose documented framework example returns the raw request body |
</threat_model>
