<objective>
Close HTTP-04: one error shape across three surfaces, proven mechanically by the test that already
proves two of them.

RESEARCH measured that the framework emits **four** different default error bodies between them —
a request-validation rejection, an unknown-route rejection, a middleware rejection that responds
before the app and therefore cannot be overridden by an exception handler, and an unhandled
exception. "No third fork" means overriding all four. It also measured that the documented handler
example for the first one returns the caller's raw request body and pydantic's `input` field, which
is precisely the disclosure class the seam's own reason builder already suppresses.

Purpose: three of Phase 18's eight green self-reports turned out to contradict criteria they
claimed met. Criterion 3 is a claim about three surfaces agreeing, and the only honest way to hold
it is the differential harness that already drives two of them for real.

Output: `model` becomes a required argument, `api/errors.py` unifies the four emitters, and the
parity table gains its third column plus a leak assertion that covers successful bodies too.
</objective>

## Named decisions recorded by this plan

- **D-24 — a capability that ran and reported failure returns HTTP 200 with its result body.** The
  result envelope separates "the command ran" from "how it went", the CLI turns the former into an
  exit code, and Phase 11's decision that a degraded curation run exits 0 is a statement about that
  flag. Mapping a reported failure onto a 4xx would re-fork the contract the exit code already
  encodes. Only the seam's own typed errors carry a status: capability-not-found maps to 404, an
  input rejection maps to 422, and the pre-dispatch guard rejections keep 400/403/401. —
  *Reversibility: reversible* (one mapping table).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| exception / validation error -> response body | The last place an environment detail or a caller's submitted value can be stopped |
| framework defaults -> response body | Three of the four emitters are the framework's, not this project's, and two of them disclose by default |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-19-16 | Information disclosure | request-validation handler | high | mitigate | The reason is built through the seam's own builder, which already suppresses the echoed input and context; the documented framework example returning the raw request body is explicitly rejected |
| T-19-06 | Information disclosure | unexpected-exception handler | medium | mitigate | Rendered through the shared sanitizer, never the exception's own text; asserted against a message that embeds an absolute path |
| T-19-05 | Information disclosure | success-path bodies | medium | mitigate | The parity leak assertion runs on successful bodies as well as failing ones, across all three surfaces |
| T-19-22 | Repudiation | a reported failure re-forked into an HTTP error | medium | mitigate | A result reporting failure returns 200 with its body (D-24), so the degraded-run contract the CLI exit code encodes is not contradicted on a second surface |
| T-19-01 | Spoofing / EoP | pre-dispatch guard rendering | high | mitigate | The guard rejections now share the one body builder, so unifying the shape did not weaken the checks that produce them |
