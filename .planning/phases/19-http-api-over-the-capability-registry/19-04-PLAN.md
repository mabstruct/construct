<objective>
Finish HTTP-03 at the seam so every capability is addressable by id, with zero documented
exclusions and no special case living in the adapter.

The tracer proved one workspace-scoped capability. Three capabilities are not workspace-scoped in
the ordinary sense and each needs a genuine resolution rather than a quiet skip: `workspace.init`
takes `root` and *creates* a directory (there is no id yet), and the two `views.*` capabilities
take `install_root`, which is a different scope from a workspace and is the trust boundary itself.

Purpose: D-07 says all 29 are exposed and every exclusion is written down with a reason. The
awkward inputs are exactly the ones a plan is tempted to leave out, and leaving them out weakens
criterion 1 to a claim about 26 capabilities.
Output: a resolver with a symmetric create mode, launch-context injection for install-root scope,
and a classification guard that fails when a future capability is registered unclassified.
</objective>

## Named decisions recorded by this plan

- **D-11 — `workspace.init` uses the uniform resolve rule with the assertion inverted, and
  `views.*` receives the install root from launch context.** For creation the two gates become
  {shape, *not* in the scan} instead of {shape, in the scan}: the caller names a directory, the
  seam decides where it lands, and that is T-18-34 answered directly rather than deferred. For the
  install-root-scoped pair, the seam supplies `launch_install_root()` when the field is absent, so
  an HTTP caller reaches them by sending nothing path-shaped while the CLI's explicit
  `--install-root` continues to be honoured. Both are symmetric additions to one resolver, not
  special cases in the adapter, and the result is **zero** `COVERAGE.md` exclusions. —
  *Reversibility: costly* — the rule is shared by all three surfaces and by Phase 22's creation
  wizard.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller payload -> filesystem path | `workspace_id` is attacker-controlled and becomes a directory path inside the seam |
| launch install root -> capability scope | The install root is the authorization boundary; a caller must never be able to move it |
| creation request -> new directory | `workspace.init` writes a directory tree at a location derived from caller input |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-19-03 | Tampering / Info disclosure | `resolve_workspace_id` | high | mitigate | Shape gate before allowlist gate; the traversal family asserts `discover_workspaces` is never called and the tree is byte-identical after a rejection |
| T-19-04 | Tampering | `workspace.init` creation mode | high | mitigate | Creation resolves under the launch install root only and asserts absence, so a caller names a directory but never chooses where it lands (T-18-34 lineage) |
| T-19-17 | Elevation of privilege | `install_root` supplied by a caller | high | mitigate | The install-root-scoped pair takes the value from launch context when absent, and plan 19-05's envelope guard refuses the field outright over HTTP, so the boundary is never caller-movable from a browser |
| T-19-18 | Repudiation | a future capability registered unclassified | medium | mitigate | The classification cardinality guard fails at registration time, naming the capability, rather than producing a request-time error |
</threat_model>
