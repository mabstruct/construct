<objective>
Make the localhost trust boundary a measured control set rather than a plausible one, and prove
rejection happens before anything can run.

RESEARCH measured the framework's actual behaviour: the stock trusted-host middleware validates
`Host` only and never inspects `Origin`, and it answers a rejected host with a plain-text response
an exception handler cannot override. So Origin validation is custom middleware or it does not
exist, and folding the Host check into the same guard is what keeps one error shape across the
whole surface. The MCP specification is the source of the control set — validate `Origin`, respond
403 when it is present and invalid, bind loopback, authenticate even locally — after three separate
DNS-rebinding advisories against MCP SDKs.

Purpose: criterion 4 says a foreign `Origin`/`Host` or a missing token is refused **before it
reaches a capability**. A status-code assertion does not prove that; only an assertion about the
workspace does.
Output: the complete guard, the full measured matrix, and an ordering proof that hashes the tree.
</objective>

## Named decisions recorded by this plan

- **D-21 — an absent `Origin` header is allowed; a present-and-not-allowlisted one is refused with
  403.** `curl`, the CLI, and any scripted client send no `Origin`, and a browser always sends one
  on a cross-origin request, so requiring the header would break every non-browser client for no
  security gain. This is the MCP specification's own wording ("if the `Origin` header is present
  and invalid").
- **D-22 — the token travels in a custom header, never a query string, and no CORS middleware is
  installed.** `X-Construct-Token` is not a CORS-safelisted header, so any cross-origin request
  carrying it must pass a preflight that no CORS policy answers — the token therefore doubles as
  the CSRF control, which is what lets D-05's route shape make `Origin` validation defence in depth
  rather than the single load-bearing check. A query-string token would land in shell history,
  server logs and the `Referer` header.
- **D-23 — Host, Origin and token are checked in one middleware, in that order.** The stock
  trusted-host middleware would answer a rejected host with a plain-text body no exception handler
  can override, which would fork the error shape criterion 3 promises. One guard, one rendering.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| any web page -> loopback port | Any page the user visits can attempt requests to the local server |
| rebound DNS name -> loopback address | After a rebind the browser still sends the attacker's hostname in `Host` |
| header-carried secret -> process | The per-launch token is the only authentication on the surface |
