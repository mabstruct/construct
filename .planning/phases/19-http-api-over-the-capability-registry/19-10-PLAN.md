<objective>
Close the two verifications this phase's automated suite structurally cannot make.

Every HTTP test in Phase 19 drives the application object through a test client. That is the right
tool for the contract, and it is blind to exactly two things: whether a real socket is bound to
loopback and reachable from a separate browser process, and whether an operator can actually get
the per-launch token into that browser. The first is the literal wording of criterion 1 ("a user
starts the server with one command and reaches every registry capability from a browser"); the
second is a usability judgement that the phase's own research raised as an open question and
resolved by preference rather than by measurement.

Purpose: this phase is the hard gate for the entire milestone. A green suite over an app object,
with nobody having opened a browser, is the shape of a self-report that contradicts the criterion
it claims — which happened three times in the previous phase.
Output: a human verdict on the two rows the validation strategy already marks manual-only.
</objective>

<task type="checkpoint:human-verify" gate="blocking">
  <name>Task 1: Reach the running server from a real browser, and get the token into it</name>
  <read_first>
    - .planning/phases/19-http-api-over-the-capability-registry/19-VALIDATION.md (the Manual-Only Verifications table — these two rows are what this checkpoint closes)
    - .planning/phases/19-http-api-over-the-capability-registry/19-01-SUMMARY.md (the actual serve command, its default port, and where the token is printed and written)
  </read_first>
  <what-built>
    A loopback-bound HTTP API over the capability registry: one command starts it, one envelope route
    reaches all 30 capabilities, a discovery endpoint advertises every input schema, `Host`/`Origin`/token
    checks run before dispatch, workspaces are addressed by id, and workflow runs are startable,
    pollable, listable and resumable across surfaces. The entire automated suite drives the
    application object through a test client, which never opens a socket.
  </what-built>
  <how-to-verify>
    1. From the repository root, start the server: `.venv/bin/python -m construct.cli serve`.
       Note the URL and the token it prints. Confirm the printed URL uses the loopback address.
    2. Confirm the token file exists and is readable only by you:
       `ls -l .construct/api-token` — the mode should show owner read/write only.
       Confirm its contents match the token printed in step 1.
    3. In a browser, open the developer console on any page and issue a fetch to the discovery
       endpoint at the printed URL's `/api/capabilities`, sending the token in the
       `X-Construct-Token` header. Confirm you get a capability list back, and that it lists every
       capability rather than a subset.
    4. From the same console, POST to `/api/capabilities/workspace.status` with a JSON body whose
       payload names one of your workspaces by id, plus the same token header. Confirm you get a
       real status result.
    5. Repeat step 4 with the token header removed. Confirm the request is refused rather than
       answered.
    6. Confirm the token did not leak into anything you would not want it in: it should not appear
       in your shell history as part of a URL, and no request you made carried it in a query string.
    7. Note whether getting the token into the browser was awkward. This is a UX judgement and the
       answer is the point — Phase 21 owns token delivery for the served app and needs to know
       whether stdout plus a file is good enough.

    If any step fails, describe what happened rather than approving; the phase's automated suite
    cannot see these behaviours, so a silent pass here is a gap that reaches Phase 21.
  </how-to-verify>
  <acceptance_criteria>
    - A real browser process received a capability list from the running server at the printed loopback URL
    - The capability list the browser received holds one entry per registered capability
    - A capability invocation from the browser with the token returned a real result
    - The same invocation without the token was refused
    - The token file's mode is owner-only and its contents match the printed token
    - The operator recorded a verdict on token-delivery ergonomics for Phase 21
  </acceptance_criteria>
  <resume-signal>Type "approved" to record both manual verifications as passed, or describe what failed and on which step</resume-signal>
</task>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| real browser -> real socket | The only place the deployed trust boundary is exercised as deployed rather than as an application object |
| operator -> token | The token has to travel from a terminal into a browser without landing somewhere durable |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-19-11 | Elevation of privilege | the bound socket | high | mitigate | The operator confirms the printed URL is the loopback address and that a browser on this machine reaches it; the automated suite asserts the constant, this step asserts the deployment |
| T-19-08 | Information disclosure | token delivery in practice | high | mitigate | The operator confirms the on-disk copy is owner-only and that no request carried the token in a query string or left it in shell history |
| T-19-02 | Tampering | drive-by CSRF, as a real browser sees it | high | mitigate | The token-removed step exercises the refusal from a real browser origin, where the preflight behaviour the design relies on actually applies — this is where research assumption A3 is genuinely tested |
</threat_model>

## Flagged assumptions (unresolved edge probes)

This checkpoint is where three residues from earlier plans are exercised against reality rather
than against a test client: assumption A3 (the token header is not CORS-safelisted, so a
cross-origin request carrying it is preflighted and blocked), the deployment half of the HTTP-02
concurrency backstop (a test client does not exercise the server's socket handling), and research
open question 1 (whether stdout plus a `0600` file is adequate token delivery for the served app
Phase 21 builds). None of the three unclassified edge rows (HTTP-03, HTTP-04, HTTP-06) is closed
here; they remain carried forward as flagged assumptions in plans 19-04, 19-07 and 19-09.
