<objective>
Make "every registry capability is reachable, and adding one adds an endpoint with zero edits"
a property that is asserted rather than assumed — and advertise the declared contract on the one
surface that can carry it.

Under D-05 there is a single static route with a path parameter, so "the server module was never
hand-edited" is true by construction and a naive guard proves nothing. The guard has to assert
reachability with cardinality, driven from the registry, and it has to be shown to fail when
something is actually missing. D-06's discovery endpoint closes, on HTTP, the schema-advertising
half of GOV-01 that Phase 18's D-21 had to concede when the pinned MCP library turned out to have
no schema-override parameter.

Purpose: this project has been bitten twice by guards that assert set membership and pass over a
subset. Criterion 1 is a claim about all 29 capabilities, and it needs a test that would notice.
Output: the discovery endpoint, the machine-read coverage ledger, and a non-vacuous cardinality
guard.
</objective>

## Named decisions recorded by this plan

- **D-18 — `COVERAGE.md` lives next to the api package at `src/construct/api/COVERAGE.md` and is
  parsed by the guard.** A planning-only document cannot participate in a cardinality assertion,
  which is the whole reason D-25 named the artifact worth writing. Colocating it with the package
  it constrains means an exclusion cannot be added without touching the package, and the guard
  reads the file rather than trusting its prose. — *Reversibility: reversible* (a path in one test).
- **D-20 — the ledger has a non-capability-routes section.** `GET /api/capabilities` and (from
  plan 19-09) `POST /api/runs` are not capability routes and are deliberately outside the zero-edit
  guard's subject. Writing them down is what stops a future reader from either counting them as
  capabilities or discovering them as an undocumented surface.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client -> envelope route | The payload arrives verbatim from an untrusted client; nothing about the adapter's own source constrains it |
| registry -> advertised schema | The discovery endpoint publishes the declared contract, which becomes something callers depend on |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-19-03 | Tampering / Info disclosure | envelope payload keys | high | mitigate | Any key in `PATH_SHAPED_KEYS` is refused with 422 before dispatch, parametrised over every capability, with the install-root tree asserted unchanged |
| T-19-17 | Elevation of privilege | `install_root` sent by a client | high | mitigate | `install_root` is in `PATH_SHAPED_KEYS`, so the boundary cannot be moved from a browser; the seam supplies it from launch context instead |
| T-19-19 | Repudiation | a capability silently unreachable | medium | mitigate | Cardinality-not-membership coverage guard plus a non-vacuity meta-test, with exclusions parsed from the ledger rather than trusted as prose |
| T-19-10 | Denial of service | unbounded run spawning | low | accept | Out of scope for a single-user local proof of concept; recorded explicitly in `src/construct/api/COVERAGE.md` rather than left silent |
| T-19-20 | Information disclosure | advertised JSON Schemas | low | accept | Schemas describe the local tool's own inputs and carry no secrets; publishing them is D-06's purpose and the browser needs them to build forms |
</threat_model>
