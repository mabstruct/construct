<objective>
Fix the writer half of the byte contract, conform the SPA's event reader, and replace the pin
test with a round-trip guard strong enough to be the only drift detector left.

Purpose: the generator validates an adapted projection and then writes a different dict — the
writer/reader fork lives inside one command pair. This plan carries the writer half of D-01
(conform to the written bytes and drop the adapter tables); Plan 04 carried the model half.
Deleting the adapter tables now makes the adapter the identity function. But those tables are also the only
thing that makes `views generate` a *validating* writer, so deleting them without replacing them
would silently downgrade it to a blind writer and leave the phase depending on `views validate`
being run separately, which no workflow guarantees. And because D-03 gives up the model-level
drift detector, the round-trip guard becomes the sole remaining detector of the next fork — so it
takes the strict cardinality form rather than a set-membership form.

Output: one shared path-to-model table, a validating writer with no adapter, an SPA reader on the
canonical event shape, and a guard that fails on one extra or one missing file.
</objective>

**Correction that supersedes D-04's arithmetic.** D-04 says "assert the written-file count equals
8". That is arithmetically wrong and would have failed on its first run: the generator writes 10
data files plus the build-root version file for a one-workspace root, and the per-workspace count
scales with workspace count. D-19 restates the clause as four global files plus six per workspace
plus one — cardinality-not-set-membership is unchanged, only the arithmetic is corrected. With
D-18's two new models landed in Plan 04, no written data file is excluded from the count.

**The lesson the guard's shape encodes (WR-01).** `tests/contract/test_artifact_catalog.py`'s
set-membership guard is exactly why its hand-typed prose counts can rot: a membership assertion
proves a thing is listed, never that nothing was added. Fixing that catalog guard itself is out
of scope here; applying its lesson to this new guard is not.
</context>
