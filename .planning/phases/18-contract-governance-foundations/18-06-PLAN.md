<objective>
Make a human-review decision name the proposal it applies to, make an incomplete decision map
reject rather than write, and make a queue that changed since it was rendered detectable.

Purpose: `_resolve_decisions` zips the decision payload against the queue **positionally** and,
when the payload is short or absent, falls back to the gate's own recommendation — so a
misaligned or truncated payload silently performs a canonical write the user never approved.
`research_run`'s version is worse in a different way: it carries three decision shapes in one
function, one of them keyed on a finding URL that can be null and is not unique. These land here,
before Phase 19's API and Phase 22's review wizards are built, specifically so the API is never
constructed against the positional shape.

Output: opaque proposal ids persisted in the checkpoint, id-keyed decision resolution in both
graphs, complete-coverage rejection ahead of any apply node, a checkpoint-id ETag, and
migrate-on-read for runs already paused.
</objective>

<task type="checkpoint:decision" gate="blocking">
  <decision>The concrete form of the proposal id, the field name it is persisted under, and the shape of the resume payload keyed by it.</decision>
  <context>
D-09 fixes that ids are **opaque** — not content-derived — but deliberately leaves the form open
("sequence or uuid"). The choice is a one-way door: the id is written into
`.construct/workflow/*.sqlite` checkpoints the moment a run pauses, and it becomes the contract
Phase 19's API and Phase 22's review wizards are built against. Reverting after those phases land
would require migrating live checkpoint state back to a positional shape while paused runs exist
in users' workspaces. Confirm the door before walking through it.

Whatever is chosen, three properties are already fixed by D-09/D-10 and are not open here: the id
is opaque rather than derived from proposal content, it is guaranteed unique within a queue, and
"this id is not in this queue" is a clean rejection rather than a fallback.
  </context>
  <options>
    <option id="uuid4-hex">
      <name>Random hex id from `uuid.uuid4().hex`, persisted as `proposal_id`</name>
      <pros>Unique with no coordination and no collision reasoning; unique across runs as well as within a queue, so a decision payload cannot be replayed against a different run by accident; stdlib only; matches the "opaque" requirement most literally.</pros>
      <cons>Opaque to a human reading a checkpoint or an event log; longer in URLs and in wizard state; not sortable, so a UI wanting queue order must carry order separately.</cons>
    </option>
    <option id="run-scoped-counter">
      <name>Run-scoped sequence, persisted as `proposal_id` (for example the run id plus an ordinal)</name>
      <pros>Human-readable in logs, checkpoints and URLs; naturally sortable, so queue order survives in the id itself; trivially unique within a queue.</pros>
      <cons>Carries queue position inside the id, which invites exactly the positional reasoning GOV-02 exists to remove; requires the enqueue path to own a counter; an id that looks meaningful invites a consumer to parse it.</cons>
    </option>
    <option id="uuid4-hex-short">
      <name>Truncated random hex (first 12 characters of a uuid4 hex), persisted as `proposal_id`</name>
      <pros>Short enough for URLs and human reference while staying opaque and order-free.</pros>
      <cons>Reintroduces collision reasoning that D-09 explicitly wanted to avoid; the argument for truncation is ergonomics, which Phase 22 can solve in the UI without weakening the id.</cons>
    </option>
  </options>
  <resume-signal>Select: uuid4-hex, run-scoped-counter, or uuid4-hex-short — and confirm the persisted field name is `proposal_id` and that the resume payload is a map from that id to a decision string.</resume-signal>
